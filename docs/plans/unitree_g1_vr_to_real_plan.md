# Unitree G1 双臂遥操作采集与真机策略验证计划

本计划面向项目开发者与真机操作人员，在固定下肢和躯干的条件下，完成 Meta Quest 3S 遥操作、单任务数据采集、动作回放、BTT tokenizer 与 VLA 策略训练，以及低速真机闭环测试。优先打通一条可复现、可诊断的端到端流程，再扩大数据和任务规模。

编写日期：2026 年 10 月 5 日；实施路线更新于 2026 年 10 月 7 日，现场实测进展截至 10 月 6 日；官方软件基线于 10 月 7 日完成离线验证。开发分支：`UnitreeG1`，起点为 `real_world` 的 `0427377`。现以宇树官方 `xr_teleoperate` 为遥操作和录制基准，阶段零/一的准备工作已开始，电脑网线直连的 30 秒只读状态订阅已通过，尚未验证真机动作控制或完成任何整阶段验收；仓库已有训练框架不代表 G1 适配已经完成。文中的采集数量、频率和成功率是建议的项目目标，不是已取得的结果，也不是机器人硬件允许值。

## 目标和范围

第一轮仅学习一个固定工位的双臂任务。建议候选任务为“双手共同抓住带把手的轻质空盒，短距离移动到标记区域并放下”。实际任务必须在确认夹爪或灵巧手、双臂可达空间后选定；若硬件不适合该任务，则选择等价的低接触力双臂任务，并在正式采集前冻结任务定义。

任务需明确初始姿态、物体位置范围、目标区域、允许时长和成功判据。建议成功定义为：物体完整落在目标区域，双手释放，稳定保持 2 秒，无人工接管或保护停止。第一轮不包含行走、腰部动作、双臂交接、动态抛接和高接触力操作。

固定下肢与躯干必须通过符合具体机型要求的支撑方式及控制模式实现。不能将“向腰腿发送零目标”当作固定；需要明确支撑装置、姿态保持控制器和上肢控制器之间的权限。任何模式切换都不得造成支撑控制被意外释放。

最终交付物包括硬件配置与标定、G1 控制适配、遥操作录制器、版本化 LeRobot 数据集、回放工具、G1 tokenizer 与策略检查点、测试结果和操作说明。

基准来源为宇树官方 [xr_teleoperate](https://github.com/unitreerobotics/xr_teleoperate)，采用独立 checkout 和环境，通过配置与小范围适配接入本项目。不要整份复制进训练仓库，也不依赖浮动的 `main` 执行实验。下表是复用计划，不代表本机已经安装或验证。

| 环节 | 优先复用 | 本项目需要完成 |
| --- | --- | --- |
| Quest 输入与显示 | `televuer` 的手柄追踪、坐标变换与 XR 页面 | Quest 3S 实测、输入有效性与重定位处理、离合和相对参考审查 |
| 相机传输 | `teleimager` | 相机配置、头显显示、每路时间戳与延迟验证 |
| 双臂 IK | 官方 G1 模型与 IK | 核验模型/关节映射、固定躯干、工作空间与连续性；补齐缺失的碰撞检查 |
| 硬件执行 | 官方 arm/末端控制器、`unitree_sdk2_python` | profile、统一适配层、唯一发布者、控制权/停止/故障处理 |

## 总体流程与系统边界

```text
操作者输入：Quest 双手柄 → televuer → 官方坐标变换 / G1 IK
                                                 ↓
采集执行：                              统一执行适配层 → 官方控制器 / SDK → G1
                                                 ↓
相机：机器人相机 → teleimager → Quest 显示 + 官方录制器
状态 / 最终指令 / 时间 / 质量事件 ───────────→ 官方 episode + 补充日志
                                                 ↓
训练：字段与同步审核 → LeRobot 转换 → G1 BTT → 冻结 BTT → BAR 策略
                                                 ↓
测试：真实观测 → 策略服务 → BTT 解码 → 同一执行适配层 → G1
```

遥操作、回放和策略必须经过同一执行适配层。优先封装官方控制器，缺失功能以最小补丁补齐；官方入口若绕过适配层，必须接入后才用于正式采集。适配层负责关节映射、指令有效期、速度与加速度约束、模式仲裁、看门狗和故障记录；位姿/IK 路径与关节回放/策略路径都需有对应的工作空间和碰撞约束，不能只保护遥操作。

硬件端保持一个授权指令发布者；模式切换时清空旧目标，不允许另起原版遥操作进程与回放/策略竞争。腰腿保持控制的权限单独核验；禁用 Quest 摇杆引起的行走/转向输出。不能简单以“不开 `--motion`”代替控制模式核验，因为不同末端与模式可能使用不同控制通道。

机器人底层控制与视觉模型推理解耦：伺服线程不等待模型返回；GPU 超时、断网或进程异常时，进入预先验证的停止状态。停止与释放控制必须按本机控制模式确定，不能统一采用突然断电或锁在最后目标位置。

## 阶段零 官方基线安装与硬件配置确认

建议工作量：2 至 4 个工作日；软件安装可先推进，硬件字段在真机运动前全部核验。

1. 建立独立 `xr_teleoperate` checkout 与控制环境，按选定版本文档安装 `televuer`、`teleimager`、SDK、IK 依赖；与本仓库训练环境隔离。记录主仓库、子模块、依赖、模型和固件版本，不直接升级已验证的 SDK 环境。
2. 审查选定版本的输入/显示/末端/仿真参数、初始化、退出、回零与 DDS 发布路径。形成支持矩阵，明确哪些来自上游、哪些需补丁，不把 README 的支持声明当作故障测试结果。
3. 确认 G1 自由度配置、每臂 7 关节映射、官方夹爪型号和单位、独立或内置接口、反馈来源。尤其解决当前夹爪接口与腰腿保持控制的兼容问题。
4. 定义 `robot_profile`：左右臂与夹爪固定顺序、单位、限位、起始姿态、控制通道、腰腿控制归属与停止行为；冻结单任务、相机布置与支撑方案。
5. 分开记录 SDK 伺服频率、官方遥操作/录制循环频率、相机频率、学习采样频率。上游文档的默认录制/控制频率为 30 Hz，不等于底层伺服频率；学习数据暂评估 20 Hz，最终以同步测试冻结。

**交付与验收：** 版本清单、上游功能差距表、硬件 profile 和任务定义。环境可导入且输入模块可独立测试；未确认的硬件字段明确标记，不填猜测值。仅环境准备完成即可进入阶段一输入验证；阶段二真机运动要求全部硬件条件完成。

## 阶段一 Quest 输入、显示与官方 IK 仿真验证

建议工作量：2 至 4 个工作日；依赖阶段零的软件基线，无需真机运动。

1. 使用官方 `televuer` 的测试入口或最小只读适配入口验证 Quest 3S 双手柄，启动前确认该入口不实例化硬件控制器、不创建命令发布者。不得把官方 `--headless` 理解为只读模式；没有合适入口时新增输入诊断适配，不直接运行真机遥操作主程序。
2. 优先选择 `pass-through` 检查左右手、三轴位移、旋转和按键；记录系统/浏览器版本，完成 30 秒基础测试、追踪丢失、重定位、断网、重新进入以及 10 分钟稳定性测试。已有 `quest_record.py` 用于对照原始输入，不替代官方链路的验收。
3. 接入 `teleimager` 测试视频；先用可用测试相机验证传输，再换实际机器人相机。核验 `ego`（透视 + 第一视角小窗）或 `immersive`（机器人视角），测量延迟和丢帧。Quest 系统透视不作为策略训练图像。
4. 使用选定版本配套的官方仿真环境和 G1 IK，核验资产与末端配置、左右轴向、尺度、末端姿态、解连续性及限位。仿真通信需与真实机器人隔离；有 `--sim` 参数仍需检查实际 DDS domain、控制器和末端路径。
5. 审查并验证相对位姿、离合使能和重新接管参考重置；上游缺失时补齐。冻结适合当前操作者的参考系，明确头部转动是否改变双臂目标，防止混用自定义 WebXR 原始坐标与上游已变换坐标。
6. 假机器人故障测试覆盖过期输入、非法目标、IK 无解、断流、进程退出和重新连接。官方仿真资产若没有我们的夹爪，只能证明手臂链路，记录末端差距，不能据此宣称夹爪验证通过。

**交付与验收：** Quest 官方链路测试报告、显示与网络配置、坐标/按键映射、仿真轨迹和故障记录。连续 10 分钟无未解释跳变；输入失效可停止目标推进且恢复不自动使能。仿真不依赖已接通的真实机器人。

## 阶段二 官方控制器适配与真机单任务遥操作

建议工作量：3 至 5 个工作日；依赖阶段零硬件条件及阶段一输入/IK/故障验收。

1. 复核只读机器人状态，补齐夹爪反馈，逐项核验 profile；由现场人员验证支撑、腰腿保持、上肢接管、停止及释放控制流程。内置夹爪若只能经全身低层控制，须先完成对应支撑与保持控制设计，不能直接套用官方示例。
2. 封装上游控制器为统一接口：`read_observation`、`request_control`、`send_targets`、`stop`、`release_control`。核验构造器、退出和回零是否会发动作；通过单一授权发布路径接入，保留小范围补丁及版本记录。
3. 复用并逐项验证上游已有保护，补齐有限值/维度、限位、速度/加速度、实测状态到首目标连续性、夹爪范围、状态陈旧与看门狗。明确禁止腰腿任务目标和手柄行走指令。
4. 实现并测试 `DISARMED → READY → TELEOP / REPLAY / POLICY → STOPPING → READY`；故障进入 `FAULT`，禁止自动恢复运动。先完成假机器人故障注入，再验证真机停止行为。
5. 在无物体条件下依次验证单关节、单臂、双臂和夹爪小幅动作；随后接官方 Quest/IK 链路，核验离合松开、重定位、断网与恢复不跳变。
6. 从空载到抓取再到完整单任务，完成至少 10 次有效演示。正式多模态记录按阶段三验收，演示成功不等于数据格式与同步通过。

**交付与验收：** 基于上游的执行适配、profile、标定与单任务操作说明、演示视频及故障日志；下肢与躯干无非预期命令，连续 10 分钟无非预期跳变。首次带物体运行前由现场人员检查结果。

## 阶段三 官方录制适配与 LeRobot 数据转换

建议工作量：3 至 5 个工作日；录制器审查和模拟数据转换可与阶段一/二重叠，真机试采集依赖阶段二。

优先复用官方 `--record` 的 episode 生命周期和图像/状态/动作存储，使用 `unitree_lerobot` 转换工具作为基准。先审查所选提交实际字段、采样位置、时间戳和落盘行为，再建立“上游字段 → 本项目 schema”映射；缺失诊断信息以补充日志或最小补丁保存，不另写一套完整录制器。官方录制成功不代表 action 已是限幅后的最终执行目标，也不代表多流已同步，这两点必须用代码检查和试采证据确认。

### 原始记录与学习数据

| 字段 | 内容与规则 |
| --- | --- |
| `episode_id`、`session_id`、`frame_index` | 标识完整轨迹和采集会话；不能跨 episode 拼接动作窗口 |
| 时间 | 主机单调时间、设备原始时间、相机曝光时间或可获得的替代时间、命令发送时间、状态接收时间 |
| 图像 | 外部或头部机器人相机，条件允许时加入腕部相机；每路独立时间戳 |
| `observation.state` | 按固定顺序的实测关节和末端状态；诊断日志另存速度、错误码等 |
| `action` | 控制时刻经过约束后、实际提交给执行器的目标；不能用下一帧实测关节值替代 |
| 辅助控制日志 | VR 原始输入、IK 目标、限制前后目标、高频最终指令、模式切换与保护事件 |
| 任务与质量 | 指令、成功标记、接管事件、失败原因、丢帧与同步质量 |
| 元数据 | 机器人配置、标定版本、代码提交、固件、数据 schema、采样频率和控制单位 |

建议先采用绝对关节位置目标作为机械臂学习动作；末端使用已确定的独立控制表示。若最终采用增量动作，必须在采集、归一化、训练和执行层同时声明参考时刻和积分方式。

1. 保存原始高频数据，再离线生成固定频率样本。图像和状态必须是决策时刻已经可获得的观测；禁止通过未来帧对齐向策略泄漏信息。
2. 同一主机优先采用单调时钟；多设备估计时钟偏移与漂移，保留校准记录。测量相机和控制通道延迟，不以接收时间自动替代采样时间。
3. 缺帧、状态陈旧、时钟重置和动作不连续时标记或切断轨迹，禁止跨长时间空缺插值成正常数据。
4. 固定 `unitree_lerobot` 转换器版本，核验其 LeRobot 版本与本仓库 loader 的兼容性；根据实际夹爪表示适配为每侧 8 维、合计 16 维。转为项目依赖版本兼容的 LeRobot 数据集，校验视频、特征元数据、动作单位、任务文本、padding mask 和 episode 边界。
5. 初步同步目标：对齐误差的 P95 小于半个数据周期，无超过一个周期且未标记的关键观测陈旧。若相机条件无法满足，先调整频率与硬件，不静默放宽规则。
6. 按采集会话和 episode 划分训练、验证、测试集，建议约 80/10/10；近重复演示保留在同一集合，归一化只使用训练集或经确认的硬件范围。

**交付与验收：** 原始日志 schema、转换器、至少 10 条试采集轨迹、数据校验报告。随机逐帧检查图像、关节、指令和任务文本对应关系，确保采集后可直接构造训练 batch。

## 阶段四 动作回放与数据集扩充

建议工作量：2 至 4 个工作日验证回放，之后按质量逐批采集；依赖阶段三。

1. 优先复用 `unitree_lerobot` 的回放/可视化工具，先审查末端支持、控制路径和版本兼容性；真机回放必须经过本项目统一执行适配层。首先进行离线可视化回放，检查关节顺序、运动范围、图像同步和动作平滑性。
2. 真机回放要求机器人和物体恢复到受控初始条件；先空载回放，再验证任务。开放环回放只用于检查数据与控制链路，不作为最终策略能力证明。
3. 回放通过相同执行层，采用符合限速与加速度约束的时间缩放与插值。接触任务的速度变化可能改变结果，单独记录缩放系数。
4. 记录目标与实测轨迹误差、限速事件、执行延迟和完成情况；误差超出阶段零确定的任务容差时停止并定位原因。
5. 在试采集通过后，建议分批收集 50、100、200 条有效演示；是否扩大到更多数据由验证误差和闭环失败类型决定。保留失败及接管记录，但初版行为克隆只用已筛选的有效示范。
6. 在同一任务内引入有限的物体位置和初始姿态变化；独立保留测试布置，不根据测试结果反复挑选模型。

**交付与验收：** 回放工具、10 条代表轨迹的回放报告、首版数据集清单与哈希。采集与回放未对齐之前，不投入大规模训练。

## 阶段五 G1 tokenizer 适配与训练

建议工作量：3 至 5 个开发日，加实际训练时间；依赖有效试采集数据，可与后续扩充并行。

1. 从 G1 profile 构造维度。当前用户确认每侧为 7 个关节加 1 个独立夹爪控制量，总动作维度为 16；具体关节顺序、单位与夹爪表示由阶段零核验。若后续使用多指独立控制，必须显式扩展表示。
2. 新建 G1 BTT 配置，检查编码器、量化器、解码器、PolicyIO、测试与导出加载流程中的 7 维或 14 维假设，保持现有 RoboTwin 配置可用。
3. 重新验证左右臂同名关节是否有可共享的运动语义。现有右臂符号向量和 min/max 不得复用；若简单符号映射不足，设计明确变换或先采用独立归一化基线。
4. 第一轮保留 32 步窗口和每臂 8 个 token，减少时间结构改动。若数据为 20 Hz，窗口代表 1.6 秒；改变频率必须重新解释时域范围。
5. 先用 5 至 10 条轨迹验证可过拟合、小规模训练和保存加载一致性，再开展正式训练。FSQ 的 `[8,8,6,5]` 可作为起始配置，不视为对 G1 最优。
6. 报告每关节原始单位 MAE/RMSE、末端开合误差、动作变化率、越界比例、码字使用情况，并单独分析双臂同步误差。
7. 将重建动作送入离线检查和受控回放，验证“低重建损失”是否对应可执行轨迹。低于任务容差且没有新增非法目标，才冻结 tokenizer。

**交付与验收：** G1 tokenizer 配置、模型权重、训练集归一化、数据版本、重建报告与解码回放结果。检查点必须包含机器人 profile 和 schema 标识，错误 profile 应拒绝加载。

## 阶段六 BAR 策略训练

建议工作量：2 至 4 个开发日，加训练与调参时间；依赖阶段五通过和正式数据集冻结。

1. 新建 G1 数据与 `bar_btt_pali` 派生配置，将相机键、状态顺序、动作维度、图像预处理和指令模板与实际部署统一。
2. 加载并冻结 G1 tokenizer，把示范动作转为目标 token，训练模型由图像、状态和任务指令预测动作 token。
3. 复用 PaliGemma2 骨干。先做显存和吞吐测试，再决定全量微调或 LoRA；记录可训练参数，避免将训练方案变化与 tokenizer 效果混淆。
4. 先进行少量轨迹过拟合与端到端解码检查，再运行正式训练。现有 30 万 tokenizer 步和 3 万策略步只作历史参考，停止条件由验证曲线、数据规模和预算决定。
5. 除交叉熵外，评估生成动作误差、非法 token、解码失败、越界、动作抖动、首个动作与当前状态的差值以及推理延迟 P50/P95/P99。
6. 至少保留一个同数据、同视觉骨干的简单动作表示基线，例如 Binning；大规模 tokenizer 消融放在闭环跑通之后。

**交付与验收：** 可独立加载的策略与 tokenizer、完整配置和验证报告。输入接口一致、预测合法、可复现解码且延迟可满足下一阶段预算后，才启动影子测试。

## 阶段七 影子推理与低速闭环测试

建议工作量：3 至 5 个工作日；依赖阶段二、四、五、六的验收。

1. 影子模式：读取真实观测并运行策略，只保存预测，不发送模型动作。覆盖完整任务，检查观测新鲜度、初始动作偏差、关节范围和延迟。
2. 建立每次预测的 observation timestamp、request ID、模型版本和有效期。丢弃过期、乱序或上一 episode 的回复；模式切换时清空动作缓存并重置策略状态。
3. 明确 `H` 为预测步数，`K` 为每次执行步数。以 `H=32`、`f_data=20 Hz` 为示例，`K=1/2/4` 对应 50/100/200 ms 的动作覆盖时间。这些是设计示例，不能在未测量延迟时直接使用。
4. 第一轮优先采用同步预测、受控保持与短动作段执行以降低复杂度，同时记录保持产生的时间偏差。若任务要求连续运动，必须测量总延迟并设计异步预取；对延迟期间已过去的动作索引做明确处理，不能直接接上陈旧动作段。
5. 底层伺服持续运行，按限速轨迹跟踪目标；低速来自执行层的时间和运动约束，不是简单降低命令发送频率。限制导致严重时间扭曲时，应以同样速度重新采集示范或调整控制设计。
6. 依次开展空载短动作、单段抓取、完整任务。真机操作人员在场并可即时停止；每次异常后查日志，禁止自动重试运动。
7. 正式评估前冻结检查点、任务范围和执行参数。建议先进行 20 次调试试验，修复后再进行 30 次独立评估；同时记录成功、超时、接管、保护停止和失误原因，不删除失败回合。

**建议项目验收目标：** 在声明的固定任务分布内，30 次正式试验至少 24 次成功；成功回合无人工干预。所有回合均无失控事件，保护触发和停止事件独立统计。报告样本量和成功率区间，不能将此规模外推为通用可靠性证明。

## 关键测试与诊断顺序

| 测试层级 | 重点用例 |
| --- | --- |
| 纯软件 | 左右臂映射及逆变换、单位与维度、归一化往返、episode 边界、padding、动作时间语义 |
| 假机器人集成 | 权限竞争、非法目标、过期请求、断网、状态断流、重启、队列清空、停止状态保持 |
| 数据与模型 | 时间同步、无未来观测泄漏、按会话划分、训练统计隔离、小数据过拟合、导出加载等价 |
| 真机分阶段 | 只读 → 空载小幅动作 → 遥操作 → 回放 → 解码回放 → 影子推理 → 闭环 |

若遥操作成功但回放失败，优先检查指令语义、初态、时间对齐和控制限幅；回放成功但 tokenizer 重建失败，检查表示与归一化；重建回放成功但策略失败，再检查观测、监督和数据覆盖。延迟不达标时先解决执行队列或推理性能，不通过扩大开环动作段掩盖问题。

## 里程碑与工作安排

工作量按一名主要开发者加现场操作支持估算，包含可重叠的工作；GPU 排队、硬件采购和访问权限不计入。预计首个完整闭环需要约 5 至 8 周，硬件和任务复杂度可能延长周期。

| 时间窗口 | 里程碑 | 进入下一阶段的证据 |
| --- | --- | --- |
| 第 1 周 | M0 官方版本/环境与硬件确认；M1 Quest 输入和仿真 | 版本清单、输入/显示测试、IK 和断流证据；硬件条件完成后进入真机 |
| 第 2 周 | M2 官方控制器适配与真机遥操作 | profile、支撑/控制权、故障验收、标定与 10 次完整示范 |
| 第 3 周 | M3 官方录制、转换与回放 | 字段映射、试采集数据、同步报告、训练 batch 与代表轨迹回放 |
| 第 4 至 5 周 | M4 首版数据集与 tokenizer | 冻结数据、重建指标、解码回放 |
| 第 5 至 6 周 | M5 策略与影子测试 | 检查点、预测合法性与延迟报告 |
| 第 6 至 8 周 | M6 低速闭环与独立评估 | 完整试验清单、成功率、失败分析、复现手册 |

建议角色分工：机器人负责人确认硬件与控制条件；采集负责人维护标定与数据质量；模型负责人维护训练与评估；测试操作人员负责现场停止与复位。人员可兼任，但首次运动和完整闭环测试应有明确的现场观察与停止职责。

4. 输入通过后接 `teleimager` 和官方 G1 IK/隔离仿真，按阶段一验收，再进入阶段二。
